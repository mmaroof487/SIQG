# AI Integration Layer

Argus heavily leverages LLMs (primarily Groq's `llama-3.1-8b-instant`) to bridge the gap between natural language and structured databases, while wrapping the AI in strict security and validation constraints.

## Flow: Natural Language to Execution

```mermaid
graph TD
    NL[User: "Show top users"] --> RATE[AI Rate Limiter]
    RATE --> GUARD[Topic Guardrail]
    GUARD --> PROMPT[Inject Schema Context]
    PROMPT --> LLM[Groq LLM]
    LLM --> SQL[Raw SQL Generation]
    SQL --> VAL[SQL Validator]
    VAL --> EXEC[Execution Layer]
```

## Security & Reliability Mechanisms

### 1. Topic Guardrails (Hallucination Protection)
Before a request is ever sent to the LLM, the input is strictly scanned against a dictionary of database and SQL-related keywords. If the user asks an off-topic question (e.g., *"Write a poem"*), the request is rejected immediately, saving token costs and API overhead.

### 2. Schema Context Injection
To prevent the LLM from hallucinating table or column names, the specific database schema metadata (or the active connection's metadata) is injected directly into the system prompt.

### 3. Prompt Engineering
Argus uses strict, few-shot prompting techniques to force the LLM to output *only* valid PostgreSQL syntax without markdown formatting or conversational filler.

### 4. Zero-Downtime Fallback (Mock LLM)
If the upstream Groq API times out, rate-limits, or throws an error, the Argus Gateway seamlessly catches the exception and falls back to a deterministic `Mock LLM` generator. This mock engine uses regex pattern matching (e.g., matching "top N" or "count by") to generate a valid SQL response instantly, ensuring that demonstrations or critical dashboards never experience a hard crash.

### 5. Post-Generation SQL Validation
The SQL string generated by the LLM is treated as untrusted input. It is passed through the standard Layer 1 Security Pipeline (blocking `DROP`, `DELETE`, etc.) before reaching the execution engine.
